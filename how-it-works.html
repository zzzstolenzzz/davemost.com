How I Built This

How the Agent Stays On-Topic — and Safe

The agent has one job: answer questions about me — my work, my projects, how I think. Ask it to write your homework or debug your Python and it declines. That boundary is enforced server-side, not just suggested in a prompt.

I treat this like a security surface, not a chatbot demo. I threat-modeled it myself and hardened the paths an attacker would actually try:

  • Sanitized conversation history — the client sends prior turns for context, so that history is treated as untrusted input and cleaned before it reaches the model. That closes the obvious jailbreak: forging a fake assistant turn that pretends the guardrail already gave permission.
  • Message length caps — input length is capped so nobody can turn my API bill into a denial-of-wallet attack.
  • Per-IP rate limiting — every caller gets a per-minute budget tracked in DynamoDB; a flood gets a 429 instead of burning my Gemini quota or spamming my phone.
  • Locked-down teaching channel — the Telegram webhook that lets me add new facts checks a shared secret token on every request and only accepts commands from my own Telegram user ID.

I attack my own systems before anyone else gets the chance.

The Teaching Loop

I keep the agent current without redeploying code. When I want it to know something new about me, I just text it to a private Telegram bot. The webhook Lambda verifies it's really me — secret token plus a user-ID allowlist — then writes the fact to DynamoDB.

The Chat Lambda reads that table on every request and folds the facts into its system prompt, so the agent's knowledge grows from a text message, not a deploy pipeline.
